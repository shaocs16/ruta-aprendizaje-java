1. ¿Qué significa arquitectura hexagonal?

El negocio no debería necesitar saber si lo invoca una petición HTTP ni si guarda los datos con JPA. La arquitectura hexagonal aísla ese núcleo y lo comunica con el exterior mediante interfaces: los puertos. Las implementaciones tecnológicas son los adaptadores.

Entrada
HTTP / Controller
→
Núcleo
Caso de uso + dominio
→
Salida
Adaptador JPA / MySQL

El flujo de ejecución va de la entrada a la salida, pero las dependencias del código apuntan hacia dentro:

infrastructure → application → domain → Java estándar
infrastructure → domain

GastoController → GestionGastosUseCase ← GastoService
GastoService → GastoRepository ← GastoPersistenceAdapter

En las dos últimas líneas, ← indica que una clase implementa la interfaz situada a su izquierda. El servicio no importa el adaptador: importa su propio puerto.

  • Puerto de entrada: qué permite hacer la aplicación.
  • Puerto de salida: qué necesita la aplicación del exterior.
  • Adaptador de entrada: traduce una petición externa a un caso de uso.
  • Adaptador de salida: implementa una necesidad del núcleo con una tecnología.
No existen obligatoriamente seis capas. El hexágono es una representación del aislamiento del negocio. Se conserva la carpeta solicitada gasto_exagonal, aunque el término habitual es hexagonal.

3. Qué hay dentro de cada capa

3.1. Dominio · domain/

Define qué es un gasto y sus reglas. Solo utiliza Java estándar; no importa aplicación, Spring, HTTP, JPA ni infraestructura.

ClaseQué contiene
model/GastoModelo inmutable con ID, descripción, importe, fecha y categoría. Constructor con validaciones, getters y validarFechaNoFutura(hoy). Sin setters ni anotaciones tecnológicas.
model/CategoriaEnum original: ALIMENTACION, TRANSPORTE, VIVIENDA, OCIO, SALUD y OTROS.
exception/GastoInvalidoExceptionIncumplimiento de una regla; extiende IllegalArgumentException. No contiene estados HTTP.
exception/GastoNoEncontradoExceptionExpresa que el gasto no existe. No conoce el significado de HTTP 404.

Reglas: descripción recortada de 1 a 100 caracteres; importe positivo, máximo 2 decimales y hasta 99999999.99, compatible con DECIMAL(10,2); fecha y categoría obligatorias. Crear y actualizar rechazan fechas futuras.

El constructor valida la estructura. La regla temporal recibe la fecha actual como argumento y se ejecuta desde el caso de uso antes de guardar. Al leer una fila se reconstruye el modelo, pero no se vuelve a aplicar esa regla temporal: una consulta no es una creación.

3.2. Aplicación · application/

Orquesta operaciones y utiliza el dominio. No importa Spring, HTTP, JPA, MySQL ni infraestructura.

ElementoResponsabilidad
port/in/GestionGastosUseCaseInterfaz para listar, filtrar, buscar, crear, actualizar, eliminar y calcular el total.
port/in/ConsultarCategoriasUseCaseInterfaz para consultar las categorías.
service/GastoServiceImplementa el puerto, comprueba existencia y rangos, construye el dominio y utiliza el repositorio abstracto.
service/CategoriaServiceDevuelve los valores del enum sin acceder a una base de datos.
port/out/GastoRepositoryInterfaz propia con las operaciones de persistencia necesarias. No extiende JpaRepository.
dto/GastoCommandDatos de creación o actualización independientes del JSON, sin ID: al actualizar manda el de la URL.
dto/CalcularTotalRecord original trasladado al caso de uso: desde, hasta y totalGastos.

El servicio recibe un Clock de Java para calcular el día actual. Se configura en UTC y se sustituye por un reloj fijo en las pruebas. Los puertos se sitúan en aplicación porque describen las capacidades y necesidades de estos casos de uso; otras variantes hexagonales pueden ubicar ciertos puertos en dominio.

3.3. Entrada HTTP · infrastructure/adapter/in/web/

  • GastoController y CategoriaController conservan las rutas; solo llaman a puertos de entrada.
  • dto/GastoRequest representa el JSON recibido y lo convierte a GastoCommand.
  • dto/GastoResponse transforma el dominio en la respuesta JSON explícita.
  • dto/ApiError conserva status, error y message.
  • GlobalExceptionHandler traduce errores de negocio y de deserialización a HTTP.

El controlador no consulta JPA ni decide si un importe es válido. Los estados HTTP pertenecen al adaptador, nunca al núcleo.

3.4. Salida de persistencia · infrastructure/adapter/out/persistence/

ClaseResponsabilidad
GastoJpaEntityRepresenta la tabla gasto y contiene @Entity, @Id, @Column y @Enumerated.
GastoPersistenceMapperConversión entre modelo de dominio y entidad JPA, sin consultas ni reglas adicionales.
SpringDataGastoRepositoryExtiende JpaRepository, filtra por categoría y calcula la suma JPQL con BETWEEN y COALESCE.
GastoPersistenceAdapterImplementa el puerto de salida, invoca Spring Data y devuelve objetos del dominio.
Inversión de dependencias: el núcleo define GastoRepository y el adaptador externo lo implementa. Cambiar de almacenamiento implica otro adaptador y configuración, no reescribir las reglas del gasto. No siempre basta con cambiar la URL.

3.5. Configuración y arranque · infrastructure/config/

  1. GastosApplication, en el paquete raíz, arranca Spring Boot.
  2. Spring Data crea el repositorio JPA y Spring lo inyecta en el adaptador.
  3. BeanConfiguration crea el reloj UTC y los servicios Java.
  4. Envuelve GastoService en TransactionalGastoUseCase.
  5. Spring aplica un proxy transaccional a este decorador y lo inyecta como puerto de entrada en el controlador.

El decorador implementa la misma interfaz y delega en el servicio. Las lecturas usan transacciones readOnly; crear, actualizar y eliminar usan escritura. Buscar y guardar en una actualización forman una sola transacción, que se revierte ante un fallo de ejecución. Así, @Transactional permanece fuera de aplicación.

Una transacción no equivale a control de concurrencia optimista: este ejemplo no incorpora un campo @Version.

4. De las clases originales al nuevo diseño

En gastosEn gasto_exagonal
GastosApplicationMismo punto de arranque con un nuevo paquete.

entity/CategoriaSe mueve a domain/model sin cambiar sus valores.

repository/GastoRepositorySe separa en puerto propio, adaptador y repositorio Spring Data.

dto/CalcularTotalResultado de aplicación.

exception/GlobalExceptionHandlerAdaptador HTTP con traducción de excepciones específicas.

Mejoras intencionadas: validación también al actualizar; fecha y categoría obligatorias; importe limitado a la capacidad SQL; descripción recortada; distinción entre 400, 404 y 500; reloj UTC. El proyecto original permanece sin cambios.

5. Cada proceso, paso a paso

5.1. Crear · POST /api/v1/gastos

  1. El cliente envía JSON. Spring lo convierte a GastoRequest; un JSON inválido genera 400.
  2. El controlador transforma el request a GastoCommand y llama al puerto.
  3. El decorador abre una transacción de escritura.
  4. El servicio construye un Gasto; su constructor valida los datos.
  5. Con la fecha obtenida del reloj, se valida que el gasto no sea futuro.
  6. El servicio invoca GastoRepository.save.
  7. El adaptador convierte a entidad; Spring Data inserta la fila y MySQL genera el ID.
  8. Se reconstruye el dominio con ID, se confirma la transacción y se devuelve 201 con Location y sin cuerpo, como en el original.

5.2. Listar o filtrar · GET /api/v1/gastos

  1. Sin categoría, se llama a findAll; con ?categoria=OCIO, a findByCategoria.
  2. El decorador abre lectura; el servicio usa el puerto de salida y el adaptador consulta JPA.
  3. Las entidades se convierten a dominio y el controlador las convierte a GastoResponse.
  4. Se devuelve 200 con una lista o []. Una categoría desconocida genera 400.

5.3. Buscar · GET /api/v1/gastos/{id}

  1. El servicio comprueba que el ID sea positivo y consulta el puerto de salida.
  2. Si existe, el modelo se convierte a respuesta: 200.
  3. Si no existe, lanza GastoNoEncontradoException; el manejador la transforma en 404.

5.4. Actualizar · PUT /api/v1/gastos/{id}

  1. Se reciben todos los campos. PUT no implementa actualizaciones parciales.
  2. En una transacción de escritura se busca el gasto; si falta, se devuelve 404.
  3. Se construye un nuevo modelo con el mismo ID y se aplican las mismas reglas que en creación.
  4. Se guarda mediante el adaptador y se devuelve 200 con el gasto actualizado.
  5. Los datos inválidos generan 400 y no cambian el registro anterior.

5.5. Eliminar · DELETE /api/v1/gastos/{id}

  1. Se abre escritura y se comprueba la existencia; si no existe, 404.
  2. El adaptador elimina por el ID encontrado.
  3. Se confirma la transacción: 204 sin cuerpo.

5.6. Sumar · GET /api/v1/gastos/total

  1. Se leen desde y hasta en formato ISO, por ejemplo 2026-10-01.
  2. El servicio exige ambas fechas y desde ≤ hasta; un rango invertido produce 400.
  3. El adaptador ejecuta SUM con BETWEEN: incluye ambos extremos.
  4. COALESCE devuelve cero si no hay filas.
  5. La aplicación construye CalcularTotal y responde 200 con desde, hasta y totalGastos.

5.7. Categorías · GET /api/v1/categorias

  1. El controlador invoca ConsultarCategoriasUseCase.
  2. CategoriaService obtiene los seis valores del enum.
  3. Devuelve 200 con un array de cadenas, sin consultas ni transacción de base de datos.

5.8. Un error también tiene un flujo

El dominio o el caso de uso lanzan una excepción sin referencias HTTP. La transacción se revierte si corresponde. El adaptador de entrada captura la excepción y decide el estado y el cuerpo de respuesta. El núcleo no necesita saber cómo se comunica el error al cliente.

El original trataba cualquier RuntimeException como un 404. Aquí un fallo de persistencia no se presenta como si simplemente no existiera un gasto.

7. Cómo ejecutarlo

Requisitos: JDK 21, Maven 3.9 o posterior y MySQL 8. Se mantiene Spring Boot 4.1.2, la versión del POM original; el repositorio Maven o proxy debe poder resolverla.

Paso 1 · Preparar MySQL

Desde un cliente MySQL, con permisos para crear bases, ejecuta el script manual:

SOURCE C:/Users/0019601/Documents/ruta-aprendizaje-java/gasto_exagonal/src/main/resources/db/gastos.sql;

Adapta la ruta si has movido el repositorio. Crea gasto_exagonal_db, la tabla y datos de ejemplo. No toca gastos_db.

El SQL es de inicialización, no una migración idempotente: no lo ejecutes repetidamente sobre una base ya preparada. Hibernate usa ddl-auto: validate, por lo que comprueba las tablas, pero no las crea.

Paso 2 · Arrancar en PowerShell

cd gasto_exagonal
$env:DB_USERNAME = "root"
$env:DB_PASSWORD = "tu_password_local"
mvn spring-boot:run

Puerto predeterminado: 8081, independiente del 8080 original. Variables opcionales: SERVER_PORT, DB_USERNAME y DB_URL. No se guarda la contraseña en el proyecto.

La URL local desactiva TLS y no se añade autenticación: es un ejemplo didáctico, no una configuración de producción.

Paso 3 · Hacer una petición

$body = @{
    descripcion = "Compra semanal"
    importe = 54.30
    fecha = "2026-10-03"
    categoria = "ALIMENTACION"
} | ConvertTo-Json

$respuesta = Invoke-WebRequest -Method Post `
    -Uri "http://localhost:8081/api/v1/gastos" `
    -ContentType "application/json" -Body $body
$respuesta.Headers.Location

Invoke-RestMethod "http://localhost:8081/api/v1/gastos?categoria=ALIMENTACION"
Invoke-RestMethod "http://localhost:8081/api/v1/gastos/total?desde=2026-10-01&hasta=2026-10-31"
Invoke-RestMethod "http://localhost:8081/api/v1/categorias"

8. Cómo probarlo y aprender con él

Desde la carpeta del proyecto:

mvn test
mvn package
TestQué demuestra
GastoTestReglas del dominio, nulos, límites y fecha futura, sin Spring ni base de datos.
GastoServiceTestCasos de uso, CRUD, filtros, rangos y categorías con Mockito y reloj fijo, sin arrancar Spring.
GastosApiIntegrationTestFlujo JSON → controlador → caso de uso → JPA → H2; respuestas HTTP, consultas, suma inclusiva y errores.
TransactionAndErrorsIntegrationTestComprueba las transacciones de lectura y escritura del decorador real y la respuesta 500 sin detalles internos; simula el puerto de salida.
ArchitectureTestImports permitidos del núcleo y separación de controladores respecto a servicios concretos y persistencia.

Los tests usan H2 en memoria, declarado como dependencia de test, y sustituyen el datasource normal. No necesitan MySQL ni contraseña. Los de API con persistencia revierten sus datos al terminar. Los tests del decorador no abren una transacción de test: verifican la transacción de la infraestructura real con el puerto de salida simulado.

H2 no verifica toda la compatibilidad con MySQL: el esquema de prueba lo crea Hibernate y no se ejecuta el script SQL de MySQL. La prueba de arquitectura revisa imports del código fuente: es didáctica, no un análisis completo de bytecode.

Orden de lectura recomendado

  1. Gasto y Categoria: entiende las reglas sin pensar en una API.
  2. Puertos: identifica qué ofrece y qué necesita el núcleo.
  3. GastoService: sigue cómo se orquesta una operación.
  4. Controladores y DTOs: observa dónde comienza y termina HTTP.
  5. Adaptador JPA y mapper: localiza el cambio de representación.
  6. Configuración y decorador: comprende el cableado y la transacción.

Ejercicio: implementa el puerto de salida con un repositorio en memoria. Si puedes reutilizar el servicio sin cambiar su lógica, has entendido la ventaja de puertos y adaptadores.
